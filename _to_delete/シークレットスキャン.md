# シークレットスキャンメモ

リポジトリを公開（public 化）する前に、API キーやトークンなどの機密情報がコード・**コミット履歴**に混入していないか検査する方法をまとめる。稼働中の商用サービスを OSS 公開・ポートフォリオ公開する際の必須チェック。`gitleaks` と `trufflehog` の 2 本立てが定番。

---

## 1. なぜ必要か / 何が危険か

- `.env` や設定ファイルにあるキーを**過去に一度でもコミット**していると、たとえ今 `.gitignore` していても **履歴に残り続ける**。public にした瞬間に抜かれる。
- 危険なもの: Anthropic(Claude) / OpenAI などの API キー、Stripe など決済キー、DB 接続情報(`DATABASE_URL`)、JWT シークレット、クラウドのアクセスキー。
- 「作業ツリー（今のファイル）だけ」でなく **git 履歴全体** をスキャンするのが鉄則。

---

## 2. 2 大ツールの違い

| ツール          | 得意                                          | 特徴                                             |
| --------------- | --------------------------------------------- | ------------------------------------------------ |
| **gitleaks**    | 秘密鍵・汎用 API キー・高エントロピー文字列   | 正規表現＋エントロピーのルールベース、速い       |
| **trufflehog**  | 実在・**有効な**キーの検出                    | 検出したキーを実際に叩いて「今も生きているか」検証できる |

→ 検出の仕組みが違うため**両方かけて、両方クリーンなら安心**、という運用にする。

---

## 3. インストールと実行（macOS）

### trufflehog

```bash
brew install trufflehog

cd /path/to/repo
trufflehog git file://. --only-verified
```

- `git file://.` … ローカルの**全コミット履歴**を対象にスキャン（一時ディレクトリにクローンして走る）。
- `--only-verified` … 実際に有効なキーだけに絞って報告。まず全部見たいなら外す。
- GitHub 上のリポジトリを直接叩くことも可能: `trufflehog github --repo=https://github.com/user/repo`

### gitleaks

```bash
brew install gitleaks

cd /path/to/repo
gitleaks detect --source . -v --redact
```

- `gitleaks detect` … git のコミット履歴全体が対象（これが重要）。
- `-v` … 詳細表示、`--redact` … 検出値を伏せて出力（ログにキーを残さない）。
- レポート保存: `--report-path gitleaks-report.json`

---

## 4. 出力の読み方（実例）

### trufflehog（クリーン時）

```
finished scanning  {"chunks": 4423, "bytes": 5823311,
 "verified_secrets": 0, "unverified_secrets": 0, ...}
```

- `verified_secrets: 0` … 有効なキーなし。`unverified_secrets: 0` … 疑わしい文字列もなし。→ クリーン。

### gitleaks（クリーン時）

```
INF 295 commits scanned.
INF no leaks found
```

- `no leaks found` が出れば合格。コミット数が出るので「履歴全体を見た」ことも確認できる。

---

## 5. `.env` / `.gitignore` の最終確認

履歴に秘密ファイルが入っていないかを直接確認する。

```bash
git ls-files | grep -iE '\.env|secret|credential'
```

- 何も出なければ OK。`.env.example`（サンプル、値は空）だけならは問題なし。
- `.gitignore` に `.env` 系が入っているかも確認する。

---

## 6. 検出された場合の対応（順番が大事）

1. **該当キーを即ローテーション（再発行）**。Anthropic / Stripe / DB などのコンソールで作り直し、古いキーを無効化する。← 一度ネットに出たキーは「漏れた前提」で扱うのが鉄則。まずこれ。
2. その後、**履歴からの削除**。`git filter-repo`（推奨）または BFG Repo-Cleaner で該当ファイル/文字列を履歴ごと除去。
3. 強制 push（`git push --force`）。共同開発者がいる場合は再クローンが必要になる点に注意。

> 履歴削除だけやってローテーションを怠るのは無意味。**再発行 → 履歴クリーニング** の順。

---

## 7. GitHub 側の機能（再発防止）

- **Secret scanning**: public リポジトリでは無料で自動有効。Settings → Code security から確認。
- **Push protection**: キーを含むコミットの push を事前にブロックしてくれる。同じ場所で有効化。
- 今後の混入をそもそも防ぐなら、push protection を入れておくのが楽。

---

## 8. public / private の判断（稼働中の商用サービスの場合）

シークレットがクリーンでも、それだけで「public にしてよい」とは限らない。

- フル public にすると、**認証・マルチテナントの分離・課金/クレジット計上・レート制限**などのロジックが全部読める＝攻撃者に設計図を渡す面がある。
- 稼働中の商用 SaaS は **本体リポジトリは private** が無難。
- ポートフォリオとして見せたいなら:
  - **ライブの URL ＋ 見せる用の public リポジトリ（作り込んだ README 中心）** の二段構え。
  - README にコンセプト・主要機能・アーキテクチャ図・技術スタック・工夫した点・スクショを載せる。必要なら代表コードだけ抜粋。
- どうしても本体を public にするなら、上記のシークレット監査（履歴込み）＋キー再発行を済ませ、「公開されても破られない（隠蔽に依存しない）」設計かを見直してから。

## 9. ハマりどころ: `command not found: trufflehog`

brew で入れたのにコマンドが見つからない場合、たいてい **PATH 未通** か **未インストール**。

```bash
brew list trufflehog          # 入っているか（No such keg なら未インストール）
which trufflehog              # パスが返るか
ls -l /opt/homebrew/bin/trufflehog   # Apple Silicon の実体パス
```

- 実体はあるのに `which` が空 → PATH が通っていない。次で通す:

```bash
eval "$(/opt/homebrew/bin/brew shellenv)"
# 恒久化:
echo 'eval "$(/opt/homebrew/bin/brew shellenv)"' >> ~/.zprofile
```

- インストール直後に見つからない時は、シェルのパスキャッシュを更新: `hash -r`
- 急ぐならフルパスで直接実行: `/opt/homebrew/bin/trufflehog ...`
