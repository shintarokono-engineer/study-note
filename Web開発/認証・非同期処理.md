# 認証・非同期処理メモ

認証 SaaS とジョブキュー(Redis + BullMQ)に関する技術知識。

---

## 1. 認証 SaaS という選択肢

Web サービスの認証実装は、自前 vs 外部 SaaS の選択を最初に行います。

### 自前実装 vs 認証 SaaS

| 観点               | 自前実装(Passport.js + JWT 等)  | 認証 SaaS                      |
| ------------------ | ------------------------------- | ------------------------------ |
| 実装時間           | 数日〜数週間                   | 30 分〜数時間                  |
| セキュリティ       | 自分で担保(事故リスク高)    | プロバイダ任せ(信頼できる)  |
| OAuth(Google等)  | 自前実装が必要                  | 数行で対応                     |
| MFA / Magic Link   | 自前実装が必要                  | 標準機能                       |
| 管理画面           | 自前で作る                      | 標準提供                       |
| 月額コスト         | サーバー代のみ                  | 無料枠 + 超過分                |
| ロックイン         | なし                            | 移行コストあり                 |

**3 週間 MVP では認証 SaaS が現実解**。月間 1 万 MAU 程度までは多くの SaaS が無料枠でカバー。

### 主要な認証 SaaS の比較

| サービス       | 特徴                                            | 無料枠           |
| -------------- | ----------------------------------------------- | ---------------- |
| **Clerk**      | UI コンポーネント完成済み、DX 良好、Webhook 充実 | 月 10,000 MAU    |
| **Auth0**      | エンタープライズ向け、機能豊富                  | 月 25,000 MAU(制限あり) |
| **Firebase Auth** | Google エコシステム統合、安価                | 月 50,000 MAU    |
| **Supabase Auth** | Supabase 全体採用なら自然                   | DB 利用料に込み  |
| **AWS Cognito** | AWS 統合、エンタープライズ向け                 | 月 50,000 MAU    |

## 2. Clerk の特徴

### 提供機能

- サインアップ / ログイン UI が**コンポーネント完成済み**(`<SignIn />` `<SignUp />` を置くだけ)
- メール / パスワード、OAuth、Magic Link、MFA 対応
- セッション管理 + JWT 発行
- Webhook(`user.created` 等)で DB 同期
- Organizations 機能(マルチテナント補助)
- 管理画面で全ユーザーを閲覧・操作可能

### Clerk が選ばれる理由

- Next.js 公式 SDK(`@clerk/nextjs`)が App Router に完全対応
- DX が他の認証 SaaS より優れている(Auth0 より直感的)
- 無料枠が広い(月 10,000 MAU)
- Webhook が DB ミラー戦略と相性◎

### Webhook で User をミラーする設計

```typescript
// Clerk Webhook 受信
async function handleClerkWebhook(event: ClerkWebhookEvent) {
  switch (event.type) {
    case 'user.created':
      await db.user.create({
        data: {
          clerkUserId: event.data.id,
          email: event.data.email_addresses[0].email_address,
          name: event.data.first_name + ' ' + event.data.last_name,
        }
      })
      break
    case 'user.updated':
      // ...
    case 'user.deleted':
      // ...
  }
}
```

**Clerk が SSoT、自前 DB に同期** することで、自前 DB 内で User 関連データを完結できます。

## 3. Redis の用途

Redis = **インメモリ KVS**(Key-Value Store)。データを**メモリ上に**保持するため、PostgreSQL より遥かに高速(マイクロ秒オーダー)。

### 主な用途

| 用途                  | 説明                                            |
| --------------------- | ----------------------------------------------- |
| **キャッシュ**        | DB クエリ結果を一時保存して負荷軽減            |
| **セッションストア**  | 認証セッションの保存                            |
| **レート制限カウンタ** | 「1 分あたり 10 回まで」のカウント             |
| **ジョブキュー保存層** | BullMQ など                                     |
| **Pub/Sub**           | リアルタイム通知                                |
| **分散ロック**        | 複数ワーカー間の排他制御                        |

### データ構造の豊富さ

String / List / Set / Sorted Set / Hash / Stream / HyperLogLog 等。単純な Key-Value 以上のことが可能。

### マネージド Redis

- AWS ElastiCache: AWS 統合、最も使われる
- Upstash: サーバーレス Redis、HTTPS API でも叩ける(エッジ環境向き)
- Redis Cloud: Redis Inc. 公式マネージド

## 4. ジョブキューが必要な理由

### API リクエスト内で重い処理をしてはいけない

- レスポンス遅延(数秒以上だと UX 悪化)
- HTTP タイムアウト(LB / プロキシ層で 30〜60 秒で切られる)
- ユーザーがブラウザを閉じても処理は続行したい
- 失敗時のリトライを自動化したい

### 解決策: ジョブキュー

```
[API] ──ジョブ投入──> [キュー(Redis)]
  即座にレスポンス返却

[Worker(別プロセス)] ──取り出し──> [キュー(Redis)]
  バックグラウンドで処理実行
```

### 典型的なユースケース

- 重い計算・AI 処理(数秒以上かかる)
- 外部 API への大量リクエスト
- メール / 通知の一斉送信
- 失敗時の自動リトライが欲しい処理(Webhook 再送など)
- 定期実行(月次集計、毎時バッチ)

## 5. BullMQ の特徴と代替

### BullMQ とは

**Redis ベースの Node.js ジョブキューライブラリ**(Bull の後継、TypeScript 完全対応)。

### 機能

- リトライ(指数バックオフ等のポリシー指定可)
- 遅延実行(「5 分後に実行」)
- スケジュール実行(cron 式対応)
- Rate Limit(「1 分間に 10 ジョブまで」)
- 進捗通知(`job.updateProgress(50)`)
- 管理画面(Bull Board)
- TypeScript 型安全

### 基本的な使い方

```typescript
// Producer(API 側)
import { Queue } from 'bullmq'
const aiQueue = new Queue('ai', { connection })
await aiQueue.add('competitor-research', { projectId, query })

// Worker(別プロセス)
import { Worker } from 'bullmq'
new Worker('ai', async (job) => {
  if (job.name === 'competitor-research') {
    return await runCompetitorResearch(job.data)
  }
}, { connection })
```

### NestJS との統合

`@nestjs/bullmq` パッケージで DI コンテナと自然に統合できる。

```typescript
@Processor('ai')
export class AiProcessor {
  @Process('competitor-research')
  async handle(job: Job) {
    // ...
  }
}
```

### 代替の比較

| 候補                    | 長所                                    | 短所                                                   |
| ----------------------- | --------------------------------------- | ------------------------------------------------------ |
| **BullMQ**              | TypeScript 完全対応、機能豊富、DX 良    | Redis 必須(ただし大抵キャッシュ等で使うので問題ない) |
| **AWS SQS + Lambda**    | サーバーレス、コスト最安                 | 順序保証や進捗通知が書きにくい、ローカル開発困難       |
| **RabbitMQ**            | 高機能、エンタープライズ実績豊富        | 専用インスタンス管理、運用コスト高                     |
| **AWS Step Functions**  | ステートマシン管理、可視化              | ベンダーロック強、ローカル開発不可                     |
| **Inngest / Trigger.dev** | サーバーレスジョブキュー、DX 良       | 比較的新しい、ベンダーロック軽度                       |

### 選び方

- 既に Redis を使っている / 使う予定 → **BullMQ**
- フルサーバーレス志向 → SQS + Lambda、または Inngest
- 大量メッセージ・複雑なルーティング → RabbitMQ
- AWS 内で完結させたい + ステートマシン重要 → Step Functions

個人開発〜中規模 SaaS では **BullMQ がバランス良し**。
