# バックエンド技術メモ

Web バックエンドの汎用技術知識をまとめます。

---

## 1. Webhook の概念

### 何か

**「イベントが発生したら相手のサーバーに HTTP POST で通知する仕組み」**(Push 型通信)。

### Pull 型(API 呼び出し)との違い

| 種別             | 方向                              | タイミング                         | 例                                         |
| ---------------- | --------------------------------- | ---------------------------------- | ------------------------------------------ |
| **API 呼び出し** | クライアント → サーバー(Pull)   | クライアントが「知りたい時」       | `stripe.subscriptions.retrieve('sub_xxx')` |
| **Webhook**      | サーバー → クライアント(Push)   | サーバーで「イベントが起きた瞬間」 | `checkout.session.completed` の POST       |

### なぜポーリングでなく Webhook か

- **タイミング**: イベント発生瞬間を知る手段がない → ポーリングするしかない
- **効率**: ポーリングは無駄な API コール多発、レート制限に引っかかる
- **リアルタイム性**: ポーリング間隔分(例: 1 分)反映が遅れる
- **障害耐性**: Webhook は失敗時に送信元が自動再送、ポーリングは自前で再試行が必要

## 2. Stripe Webhook と Idempotency Key パターン

### Idempotency が必要な理由

Stripe Webhook は **同じイベントが複数回送信される仕様**(ネットワーク障害時の再送等)。同じイベントを 2 回処理すると、二重課金扱い・状態不整合が起きます。

### 解決パターン

```typescript
// 受信時の処理(疑似コード)
async function handleWebhook(event: Stripe.Event) {
  // 既に処理済みか確認
  const existing = await db.webhookEvent.findUnique({
    where: { stripeEventId: event.id }
  })
  if (existing) return  // 既処理、スキップ

  // 処理 + 記録を同一トランザクションで
  await db.$transaction([
    processStripeEvent(event),
    db.webhookEvent.create({ data: { stripeEventId: event.id, ... } })
  ])
}
```

### WebhookEvent テーブル設計

```prisma
model WebhookEvent {
  id              String   @id @default(cuid())
  stripeEventId   String   @unique          // ← Idempotency Key
  type            String
  payload         Json
  status          WebhookStatus @default(PROCESSED)
  processedAt     DateTime @default(now())

  @@index([type, processedAt])
}
```

`stripeEventId @unique` 制約があれば、万一トランザクション外で重複しても DB レベルで弾けます。**ユニーク制約で構造的に重複を防ぐ** のがベストプラクティス。

### WebhookEvent テーブルの役割

1. **Idempotency 担保**: ユニーク制約で重複処理を防ぐ
2. **トラブルシューティング**: 過去のペイロードを参照可能
3. **監査**: いつどんなイベントを受信したかの記録

## 3. マルチテナント設計

「マルチテナント」= 1 つのシステムを複数の組織(テナント)で共有する設計。Slack や Notion 等の B2B SaaS の主戦場。

### マルチユーザーとの違い

- **マルチユーザー**(Twitter 型): 全員が同じ場所にデータを置く、ユーザー間に組織概念がない
- **マルチテナント**(Slack 型): 組織概念あり、組織内はデータ共有、組織間は完全分離

### 3 つの分離方式

| 方式       | DB 構成                                  | データ分離           | 例                         |
| ---------- | ---------------------------------------- | -------------------- | -------------------------- |
| **Pool**   | 全テナント共有 DB、tenantId カラムで識別 | アプリケーションロジック | Slack、Notion(初期)      |
| **Bridge** | 共有 DB、テナント毎にスキーマ分離       | 物理(スキーマ単位)   | 一部エンタープライズ SaaS  |
| **Silo**   | テナント毎に DB を分ける                 | 完全独立(最強)       | 規制業界、エンタープライズ |

### Pool model の長所と落とし穴

**長所**:

- 単一 DB で運用コスト最小化
- マイグレーション・バックアップ運用が一元化
- スケール時に一部テナントを Silo に切り出すハイブリッド化が可能

**落とし穴と対策**:

- **アプリケーションのバグでテナント漏洩しうる** → ORM 層(Prisma Client Extension 等)で `tenantId` を**自動注入**する設計が定石
- **Raw SQL は禁止** または `WHERE tenantId = $1` を必須化、ESLint カスタムルールで検出
- **Noisy Neighbor 問題**(大規模テナントが他に影響)→ 監視で検知、必要時 Silo 切り出し

## 4. テナントを URL で表現する方式

ワークスペース(テナント)切替時、どの方式で「現在のテナント」を識別するかは設計判断。

### 3 つの方式

| 方式             | URL 例                              | 採用例                       |
| ---------------- | ----------------------------------- | ---------------------------- |
| **サブドメイン** | `acme.app.com`                      | Slack、Notion、Zendesk       |
| **サブパス**     | `app.com/w/{slug}`                  | GitHub Orgs、Linear、Vercel  |
| **JWT 埋め込み** | `app.com/dashboard`(URL に出ない) | エンタープライズ SaaS の一部 |

### 比較

| 観点         | サブドメイン           | サブパス               | JWT 埋め込み                 |
| ------------ | ---------------------- | ---------------------- | ---------------------------- |
| SSL          | ワイルドカード証明書必要 | 単一証明書で OK       | 単一証明書で OK             |
| DNS          | 動的 DNS 必要          | 不要                   | 不要                         |
| URL 共有     | テナントが明示される   | テナントが明示される   | 別テナント環境を見せられない |
| ブランド     | 「自分の」感が強い    | 普通                   | 普通                         |
| 開発環境     | localhost に工夫が必要 | 簡単に再現可能         | 簡単に再現可能               |
| 認可ミス     | URL で気付きやすい     | URL で気付きやすい     | URL に出ないため検知困難     |

### 判断基準

- 個人開発・小規模 SaaS: **サブパス**(SSL / DNS の運用コスト低)
- ブランディング重視・エンタープライズ: **サブドメイン**
- B2C で組織概念を見せない設計: **JWT 埋め込み**

Vercel / Linear / GitHub などのモダン B2B SaaS は **サブパス方式** がデファクト気味。

### slug の役割

サブパス方式では URL に登場する `slug`(`devlog` `acme-corp` 等)が必要:

- データベース上の ID は `cuid` 等で URL に出すと汚い
- 人間可読・記憶可能・グローバルにユニークな ID が必要
- 命名ルール: 英数字 + ハイフン、3〜30 文字、予約語チェック

## 5. 招待トークン設計(InvitationToken パターン)

メンバー招待の URL `app.com/invite/{token}` の `{token}` を管理するパターン。

### なぜ DB テーブルが必要か(JWT で代替できない理由)

| 必要な機能         | DB テーブル          | JWT のみ                          |
| ------------------ | -------------------- | --------------------------------- |
| 受諾済みの記録     | ✅                   | ✗(JWT は state-less)            |
| 招待の取消         | ✅                   | ✗(JWT は満了まで有効、削除不可) |
| 招待状況の一覧表示 | ✅                   | ✗                                 |
| 重複招待の制御     | ✅                   | ✗                                 |
| 不正アクセス防止   | ✅(暗号学的乱数)   | ✅                                |

### スキーマ例

```prisma
model InvitationToken {
  id           String    @id @default(cuid())
  tenantId     String
  email        String
  role         Role
  token        String    @unique  // 暗号学的乱数 32 文字推奨
  expiresAt    DateTime            // 7 日後など
  acceptedAt   DateTime?
  invitedById  String

  @@index([tenantId, email])
  @@index([token])
}
```

### 設計のポイント

- **有効期限**: 7 日程度が標準。古いリンクが永遠に有効だとセキュリティリスク
- **重複招待**: 同じメールへの再招待で別トークンが乱立しないよう、既存トークンを更新
- **トークン生成**: 推測不可能な暗号学的乱数(`crypto.randomBytes(24).toString('base64url')` 等)
- **メンバー数上限**: 招待発行時にサーバ側で検証(プラン制限の整合性)

### 招待フローの基本形

```
1. 管理者: 「user@example.com を REVIEWER ロールで招待」
   ↓
2. InvitationToken レコード作成 + メール送信
   ↓
3. 招待者がリンクを開く
   ↓
4. 認証(未登録ならサインアップ)
   ↓
5. 受諾画面で「参加する」
   ↓
6. TenantMember レコード作成 + InvitationToken.acceptedAt を更新
```
