# モノレポメモ

Monorepo / Turborepo / pnpm Workspaces / pnpm-workspace.yaml をまとめます。

---

## 1. Monorepo vs Polyrepo

### 何か

| 方式           | 構成                                                |
| -------------- | --------------------------------------------------- |
| **Monorepo**   | 複数のアプリ・パッケージを **1 つの git リポジトリ** で管理 |
| **Polyrepo**   | アプリ・パッケージごとに **別々のリポジトリ** で管理     |

### Monorepo のメリット

- **共通コード(型・UI・スキーマ)を簡単に共有**できる
- フロントとバックの**型同期**: API 仕様変更時、フロントのビルドエラーで即座に検知
- **1 PR でフロント+バックの変更を同時レビュー**可能
- 依存関係の整合性管理が楽(全 workspace で同じ React バージョン等)
- 横断的な refactor がしやすい

### Monorepo のデメリット

- リポジトリサイズが大きくなる(数年経つと git 操作が重くなる、Sparse Checkout で緩和)
- 権限分離ができない(誰でも全コードにアクセス)
- ビルドツールの工夫がないと CI が遅くなる(→ Turborepo 等が解決)

### Polyrepo のメリット

- リポジトリ単位で権限分離可能
- 独立デプロイ・独立リリースが綺麗
- マイクロサービス志向と相性◎

### どちらを選ぶか

| 状況                                            | おすすめ      |
| ----------------------------------------------- | ------------- |
| 個人開発・小規模チーム・複数 app + 共有 lib    | **Monorepo**  |
| マイクロサービス、複数チーム、独立性重視        | Polyrepo      |
| Vercel / Linear / Stripe のような統合 SaaS     | Monorepo 寄り |

現代の B2B SaaS では Monorepo + Turborepo の組み合わせが事実上のデファクト。

## 2. Monorepo ツール比較

| ツール        | 言語   | 機能                                     | 学習コスト | 用途                       |
| ------------- | ------ | ---------------------------------------- | ---------- | -------------------------- |
| **Turborepo** | Rust   | キャッシュ + 並列実行、シンプル         | 低         | Vercel 推奨、現代の主流    |
| **Nx**        | TS     | 機能豊富、可視化、大規模対応            | 高         | エンタープライズ、Angular |
| **Lerna**     | TS     | 古典的、現在はメンテモード               | 中         | レガシー継承               |
| **Rush**      | TS     | Microsoft 製、設定重い                   | 高         | Microsoft プロジェクト     |
| **Bazel**     | Java   | Google 製、超大規模対応、polyglot       | 極高       | Google 規模の大規模開発    |

### 選び方

- 個人開発〜中規模 SaaS: **Turborepo**
- Angular / 大規模エンタープライズ: Nx
- Microsoft エコシステム: Rush
- 多言語(Go + Java + Python 等)の超大規模: Bazel

## 3. Turborepo の中核機能

### キャッシュ

変更されたパッケージとその依存だけを再ビルド・再テスト。同じ入力なら成果物をキャッシュから返す。

```
1 回目の build: 全パッケージ実行(数十秒)
2 回目の build: キャッシュヒット(< 1 秒)
1 つだけ変更後の build: 変更パッケージ + 依存先のみ実行(数秒)
```

### 並列実行

依存関係を自動解決し、可能な限り並列で実行する。

```
packages/ui のビルド ─┐
                       ├─→ apps/web のビルド
packages/types のビルド┘
```

### リモートキャッシュ

Vercel と統合すると、CI のキャッシュをチーム全員で共有できる(無料)。

- 開発者 A がローカルで build → キャッシュが Vercel にアップロード
- 開発者 B が同じコードを clone → ビルドせずキャッシュをダウンロード
- CI も同じキャッシュを共有

### turbo.json の基本

```json
{
  "$schema": "https://turbo.build/schema.json",
  "tasks": {
    "build": {
      "dependsOn": ["^build"],          // 依存パッケージの build を先に実行
      "outputs": ["dist/**", ".next/**"] // キャッシュ対象の出力先
    },
    "dev": {
      "cache": false,         // dev サーバーはキャッシュしない
      "persistent": true       // 長時間動くプロセスを宣言
    },
    "lint": { "dependsOn": ["^build"] },
    "test": { "dependsOn": ["^build"] }
  }
}
```

`^` は「依存パッケージ先の」を意味する。`apps/web` の build は `packages/ui` の build 完了後に実行される。

## 4. pnpm Workspaces の特徴

### pnpm 自体の強み

| 観点         | pnpm                                  | npm / yarn                  |
| ------------ | ------------------------------------- | --------------------------- |
| インストール速度 | 速い(並列 + キャッシュ最適化)      | npm < yarn < pnpm           |
| ディスク効率 | **ハードリンク方式**(同パッケージ重複しない) | 各 node_modules で重複     |
| Workspaces   | 標準サポート(別ファイル設定)        | npm: 配列、yarn: 配列      |
| Strict 解決  | 宣言されていない依存を使えない(隠れた依存防止) | npm はゆるい                |

### ハードリンク方式の威力

通常: 1000 プロジェクトで lodash@4.17.21 を使うと、各 node_modules に 1000 個コピー → 数 GB
pnpm: 1000 プロジェクトで lodash@4.17.21 を共有 → 数 MB

### Workspaces の効用

```bash
# workspace 間のローカルリンク
pnpm add @shipyard/types --filter @shipyard/web
# ↑ npm レジストリではなく、ローカルの packages/types への symlink を作る

# 特定 workspace のスクリプト実行
pnpm --filter @shipyard/web dev

# 全 workspace 一括実行
pnpm -r build
```

### catalog 機能(pnpm 9+)

複数 workspace で同じバージョンを使う依存を一元管理:

```yaml
# pnpm-workspace.yaml
packages:
  - 'apps/*'
  - 'packages/*'

catalog:
  react: ^19.0.0
  typescript: ^5.5.0
```

```jsonc
// 各 workspace の package.json
{
  "dependencies": {
    "react": "catalog:"  // ← pnpm-workspace.yaml の catalog から解決
  }
}
```

「全 workspace で同じバージョン」を構造的に保証できる。

## 5. pnpm-workspace.yaml の役割

### 何のファイルか

**pnpm が monorepo(workspace)を認識するための設定ファイル**。npm / yarn は `package.json#workspaces` を使うが、pnpm は独立した YAML ファイルを使う。

### 最小構成

```yaml
packages:
  - 'apps/*'      # apps/ 直下の各ディレクトリ
  - 'packages/*'  # packages/ 直下の各ディレクトリ
```

このファイルがないと workspace 機能が一切効かなくなる。

### なぜ pnpm だけ別ファイルか

pnpm は workspace に関する高度な設定(catalog / packageExtensions / overrides)を YAML で書けるよう設計されている。`package.json` に詰め込むと冗長になるため。

### 拡張例

```yaml
packages:
  - 'apps/*'
  - 'packages/*'
  - '!**/test/**'  # test ディレクトリは除外

catalog:
  react: ^19.0.0
  typescript: ^5.5.0

# 特定パッケージの peer dependencies を上書き
packageExtensions:
  '@some/lib':
    peerDependencies:
      react: '*'
```

## 6. apps/ と packages/ の責務分離(片方向依存原則)

### 階層概念

| 階層        | 性質                                              | 例                                  |
| ----------- | ------------------------------------------------- | ----------------------------------- |
| `apps/`     | **実行可能アプリケーション**(プロセスを起動)    | Web サーバー、API サーバー          |
| `packages/` | **共有ライブラリ**(他から import される)        | DB 層、UI、型定義                  |

### 依存方向のルール

- `apps/* → packages/*`: ✅ OK
- `apps/* → apps/*`: ❌ NG(暗黙の起動順依存が生まれる)
- `packages/* → apps/*`: ❌ NG(共有ライブラリが特定アプリ実装に依存)
- `packages/* → packages/*`: ✅ OK(循環依存は別途禁止)

ESLint カスタムルール(`eslint-plugin-import` の `no-restricted-paths`)で構造的に強制可能。

## 7. DB 層を packages に置く一般的な理由

ORM(Prisma など)のスキーマと Client は `apps/api/prisma/` ではなく **`packages/db/` に配置するのが現代の主流**。理由:

### 1. consumer が複数想定されるため

DB を直接利用するのは API ハンドラだけではない:

- API ハンドラ
- Background Worker(BullMQ)
- Webhook 受信処理
- マイグレーション実行(CI)
- Seed スクリプト
- 管理用 CLI / 運用スクリプト
- 将来の admin app

これらが同じ Prisma Client を共有する必要があるため、共有パッケージ化が自然。

### 2. 型を `apps/web` から参照可能

```typescript
// packages/types/api/project.ts
import type { Project } from '@shipyard/db'  // Prisma 生成型を共有

export type CreateProjectRequest = Omit<Project, 'id' | 'createdAt'>
```

`apps/api` 内に閉じ込めると `apps/* → apps/*` の依存になり、片方向依存原則に違反。

### 3. ORM の Extension(マルチテナント自動注入等)を全 consumer で再利用可能

```typescript
// packages/db/src/extensions/tenant-injection.ts
export function tenantInjectionExtension() { ... }

// packages/db/src/index.ts
export const db = new PrismaClient().$extends(tenantInjectionExtension())
```

API ハンドラ・Worker・Seed・管理 CLI 全てで同じ Extension を享受できる。

### 4. migration 実行の責務が独立

CI で `pnpm --filter @shipyard/db migrate deploy` を実行すれば、API のデプロイサイクルから独立してマイグレーションできる。

### 5. 業界の事実上のデファクト

Turborepo 公式テンプレート(`with-prisma`)、T3 Turbo、Cal.com、Vercel Commerce など全てこの構成。
