# Terraform メモ

インフラをコードで宣言し、差分を実環境に適用するツール(IaC)の基本をまとめます。

---

## 1. Terraform とは

**IaC(Infrastructure as Code)ツール**の一つです。AWS CDK とは同じカテゴリの競合であり、どちらか一方を選びます。

| | Terraform | AWS CDK |
| --- | --- | --- |
| 提供元 | HashiCorp | AWS 公式 |
| 記述言語 | HCL(専用言語) | TypeScript / Python など汎用言語 |
| 内部の仕組み | 独自の state で差分を管理 | CloudFormation に変換して実行 |
| 対象範囲 | AWS 以外も可(GitHub / Cloudflare / Datadog など) | AWS 中心 |

Terraform は**宣言型**です。「こう作れ」という手順ではなく「最終的にこうなっていてほしい」を書きます。

---

## 2. 3 つの要素

Terraform の動作は、この 3 つを突き合わせて差分を埋めることに尽きます。

| 要素        | 実体             | 役割                                  |
| --------- | -------------- | ----------------------------------- |
| **設定**    | `*.tf` ファイル    | **あるべき姿**。人が書く                      |
| **state** | S3 等に保存されるファイル | Terraform が「自分が作った」と認識しているものの**台帳** |
| **実体**    | クラウド上の本物       | 実際に存在するリソース                         |

state があるため、Terraform は「設定に書いてあるが実体が無い」「実体はあるが設定から消された」といった差分を判別できます。

---

## 3. plan と apply

```
terraform plan
  ① refresh : 実体を読みに行き state を最新化する
  ② 比較    : 「設定」と「実体」を突き合わせる
  ③ 出力    : 差分を表示する(変更はしない)

terraform apply
  ①〜③ に加えて ④ API を呼んで差分を埋める
```

`apply` は `plan` + 実行です。本番では次のように分けると安全です。

```bash
terraform plan -out=plan.tfplan   # 差分をファイルに保存
terraform apply plan.tfplan       # そのファイルをそのまま実行
```

保存した plan を渡すと**確認プロンプトが出ず、レビューした内容だけが実行されます**。plan と apply の間に誰かが環境を触っていても、意図しない変更が混ざりません。

### 差分の記号

| 記号 | 意味 | 注意 |
| --- | --- | --- |
| `+` | 新規作成 | |
| `~` | 既存を残したまま更新 | |
| `-/+` | **一度削除してから作り直す** | 本番でこれが出たら要確認 |
| `-` | 削除 | `to destroy` が 0 でないときは中身を必ず見る |
| `<=` | data source の読み取り | |

サマリの `Plan: 8 to add, 1 to change, 0 to destroy.` が、それぞれ `+` / `~` / `-` の件数です。

## 4. 管理から外す — `ignore_changes`

`lifecycle` ブロックの `ignore_changes` で、設定に書いてある属性を管理対象から外せます。

### 重要な性質: 作成時は適用され、更新時だけ無視される

| 状況 | 動き |
| --- | --- |
| 初回作成 | **設定どおりの値で作られる**(`ignore_changes` は効かない) |
| 以後の更新 | 差分を無視する。手で変えた値がそのまま残る |

そのため「新規環境を建てるときは問題ないが、稼働中の環境に手を入れると挙動が変わる」という罠が生まれます。

### 使いどころ

「その属性の正を Terraform 以外が持っている」場合に使います。

| 例 | 正を持つのは |
| --- | --- |
| コンテナのイメージタグ | CI/CD(デプロイのたびに更新する) |
| DB のエンジンバージョン | クラウド側(マイナーバージョン自動アップグレード) |
| シークレットの値 | 人間(CLI で手動投入する) |

---

## 5. 何を管理し、何を管理しないか

```
Terraform が持つもの
  ├─ どんなリソースが存在するか
  ├─ どう繋がっているか(ネットワーク・セキュリティグループ)
  ├─ 誰が何をできるか(IAM)
  └─ 非機密の値(ドメイン名・インスタンスサイズ・CIDR など)

Terraform が持たないもの
  ├─ 機密の値                    ← 設計判断。後述
  ├─ 他の自動化が正を持つ属性    ← ignore_changes
  ├─ リソースの「中身」          ← DB のテーブル・ユーザーなど
  └─ クラウド外の設定            ← GitHub / SaaS のダッシュボード設定
```

「値は Terraform で管理しない」という理解は誤りです。**大半の値はコードで管理します。** 分かれ目は機密かどうかです。

### 機密値を外す理由

Terraform は機密値も**書けば動きます**。避けるのは、値が **state に平文で記録される**からです。state はストレージに置かれ `terraform show` で読み出せるため、state を読める全員に本番の認証情報が見える状態になります。

そこで「Terraform は箱とキー構造だけ作り、中身は CLI で直接投入する」という設計を採ることが多いです。

---

## 6. drift(手動変更とのズレ)

管理下の属性を手で変更すると、次の `plan` が **drift** として検出します。裏を返せば、一時的に手で変えても `plan` が `No changes.` に戻れば、完全に復元できたと機械的に確認できます。

**`-refresh=false` は付けない。** state が最新化されず、`ignore_changes` のある属性は**古い値をクラウドに書き戻します**(デプロイ済みイメージの巻き戻り等)。

---

## 7. まとめ

- Terraform は「設定 / state / 実体」の差分を埋めるツール
- `apply` は `plan` + 実行。本番では plan をファイルに保存してから適用する
- `ignore_changes` は管理から外す指定。**作成時は適用され、更新時のみ無視される**
- 機密値を外すのは Terraform の制約ではなく、**state に平文を残さないための設計判断**
- 管理下の属性は手で変えても `plan` で検出できる。これが安全網になる
