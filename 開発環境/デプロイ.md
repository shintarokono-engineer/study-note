# デプロイとホスティング

アプリを世に出すための仕組み(デプロイ・ホスティング・CI/CD)と、Vercel をはじめとするモダンなプラットフォームの位置付けをまとめます。

---

## 1. デプロイとホスティングの違い

| 用語             | 種別           | 意味                                                                |
| ---------------- | -------------- | ------------------------------------------------------------------- |
| **デプロイ**     | 行為・プロセス | ソースコードを「動く形」にして実行環境に配置する **行為**           |
| **ホスティング** | サービス       | アプリを実行・公開するためのサーバー基盤を **提供するサービス**     |

両者の関係:「**ホスティングサービスにアプリをデプロイする**」。

### イメージで言うと

- **ホスティング** = レストランの「物件・厨房・スタッフ」を借りる
- **デプロイ** = 「料理を作って厨房に運び込む」行為
- **アプリの稼働** = 「お客さんが食事を楽しんでいる状態」

レストラン物件があっても料理を運ばなければ何も提供できないし、料理だけあっても物件がなければ提供できません。

---

## 2. ホスティングサービスの分類

歴史的経緯と抽象化レベルで分類します。

| 種類                 | 抽象度 | 提供範囲                                | 典型的なデプロイ方法                       | 代表例                                  |
| -------------------- | ------ | --------------------------------------- | ------------------------------------------ | --------------------------------------- |
| **レンタルサーバー** | 低     | サーバー領域(共有)                    | FTP でファイル転送                         | さくら、ロリポップ                      |
| **VPS**              | 低     | 仮想専用サーバー                        | SSH ログイン → git pull → 自前で再起動    | ConoHa、Linode、DigitalOcean            |
| **IaaS**             | 中     | 仮想マシン + ネットワーク + ストレージ  | AMI / コンテナ + Auto Scaling 設定        | AWS EC2、GCP Compute Engine             |
| **コンテナ PaaS**    | 高     | コンテナ実行環境(LB / スケール内蔵)   | Docker イメージ push → 自動デプロイ       | AWS ECS Fargate、Cloud Run              |
| **PaaS**             | 高     | 言語ランタイム + DB + LB の一体提供     | git push → 自動ビルド・デプロイ           | Heroku、Railway、Fly.io                 |
| **静的ホスティング** | 高     | 静的ファイル配信 + CDN                  | ビルド済みファイル転送 → 自動配信         | Netlify、GitHub Pages、Cloudflare Pages |
| **Vercel**           | 高     | 静的 + サーバーレス関数 + Edge Network  | git push → 自動ビルド・デプロイ・配信     | Vercel                                  |
| **サーバーレス**     | 最高   | 関数実行環境のみ(リクエスト時に起動)  | 関数コード ZIP アップロード                | AWS Lambda、Cloudflare Workers          |

抽象度が高いほど「インフラを意識せずデプロイできる」が、自由度は下がります。

### 選び方の目安

| 状況                              | おすすめ                          |
| --------------------------------- | --------------------------------- |
| 個人サイト・ブログ                | Vercel / Netlify / Cloudflare Pages |
| Next.js / Remix のフロント        | **Vercel**(完璧な統合)         |
| Node.js / NestJS の API           | コンテナ PaaS(ECS Fargate / Cloud Run) |
| カスタム要件強・大規模            | IaaS(AWS / GCP)                |
| イベント駆動・低トラフィック      | サーバーレス(Lambda / Workers) |

## 3. デプロイのプロセス

「デプロイ」は単なるファイル転送ではなく、以下の一連のプロセス全体を指します。

```
1. ビルド         (TypeScript → JS、CSS バンドル、画像最適化 等)
   ↓
2. パッケージ化   (Docker イメージ作成、静的ファイル zip、Lambda ZIP 等)
   ↓
3. アップロード   (レジストリ / ストレージ / Edge Network へ転送)
   ↓
4. 環境設定       (環境変数・シークレット注入)
   ↓
5. 切り替え       (旧バージョンから新バージョンへ、ローリング更新等)
   ↓
6. ヘルスチェック (新バージョンが正常稼働しているか確認)
```

### 切り替え戦略

| 戦略                   | 内容                                                          | 用途                                |
| ---------------------- | ------------------------------------------------------------- | ----------------------------------- |
| **即時(Recreate)**   | 旧を停止 → 新を起動                                           | ダウンタイム許容できる小規模        |
| **ローリング**         | 一部のインスタンスから順次新バージョンに置き換える            | 中規模、ECS / Kubernetes デフォルト |
| **Blue-Green**         | 新環境を完全に立ち上げてからルーティングを一気に切り替え      | 一発切替・即ロールバック可能        |
| **カナリア**           | 新バージョンに少数(5%)だけトラフィックを流して様子を見る    | リスクの高い変更                    |

## 4. CI / CD との関係

### 4.1 用語の整理

| 用語                                        | 意味                                                                              |
| ------------------------------------------- | --------------------------------------------------------------------------------- |
| **CI**(Continuous Integration)            | 自動テスト・lint 等の品質チェックを継続的に実施する仕組み                         |
| **CD**(Continuous Delivery)               | 「リリース可能な状態」を常に保つ(本番反映は手動 GO サイン)                     |
| **CD**(Continuous Deployment)             | 自動で本番反映まで行う(Delivery より一歩進んだ自動化)                          |

「デプロイ」は **CD の構成要素の 1 つ**。CI/CD パイプライン全体は以下のような流れです。

```
[git push]
   ↓
[CI: 自動テスト・lint・typecheck]
   ↓
[ビルド・パッケージ化]
   ↓
[CD: ステージング環境へデプロイ]
   ↓
[E2E テスト・受入確認]
   ↓
[CD: 本番環境へデプロイ]
   ↓
[ヘルスチェック・監視]
```

### 4.2 主要な CI/CD プラットフォームの比較

| プラットフォーム      | 特徴                                                                  | 料金                            |
| --------------------- | --------------------------------------------------------------------- | ------------------------------- |
| **GitHub Actions**    | GitHub と完全統合、最も普及、デファクト                              | パブリック無料、プライベート月 2,000 分まで無料 |
| GitLab CI/CD          | GitLab と統合、UI が見やすい                                          | 月 400 分まで無料               |
| CircleCI              | 高速、設定が柔軟                                                     | 月 6,000 分まで無料             |
| Jenkins               | OSS、自前ホスト                                                      | 無料(自前運用コスト)         |
| Travis CI             | OSS で広く使われていたが、有料化以降シェア減                         | -                               |

GitHub に lock-in されている時代(2026 年現在)では **GitHub Actions が事実上のデファクト**。

### 4.3 GitHub Actions の基礎

#### ファイル配置

`.github/workflows/` 配下に YAML ファイルを置くだけで動きます(ファイル名は任意、複数ファイル可)。

```
.github/
└── workflows/
    ├── ci.yml         # PR ごとの lint / test
    ├── deploy.yml     # デプロイ専用
    └── nightly.yml    # 夜間バッチ
```

#### YAML ファイルの基本構造

```yaml
name: CI

on:                 # トリガー
  push:
    branches: [master]
  pull_request:
    branches: [master]

concurrency:         # 同時実行制御
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint-and-format:   # ジョブ ID(任意)
    name: Lint & Format Check
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
        with:
          version: 10
      - uses: actions/setup-node@v4
        with:
          node-version-file: '.nvmrc'
          cache: 'pnpm'
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm format:check
```

### 4.4 各セクションの解説

#### `on:`(トリガー)

ワークフロー起動条件を定義します。

| トリガー                         | 内容                                                          |
| -------------------------------- | ------------------------------------------------------------- |
| `push: branches: [master]`       | `master` への直接 push 時                                    |
| `pull_request: branches: [master]` | `master` をターゲットにした PR の作成・更新時               |
| `workflow_dispatch:`             | UI から手動実行ボタンで起動                                  |
| `schedule: - cron: '0 0 * * *'`  | 定時実行(夜間バッチ等)                                    |
| `release: types: [published]`    | リリース作成時                                                |

#### `concurrency:`(同時実行制御)

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

| 設定                  | 意味                                                                                         |
| --------------------- | -------------------------------------------------------------------------------------------- |
| `group`               | 「同じグループ」とみなすキー(ワークフロー名 + ブランチ名等)                              |
| `cancel-in-progress`  | `true` なら新しい実行が来た時、古い実行を**キャンセル**                                    |

**なぜ必要か**:

- PR 中に何度も push すると、CI が古いコミットに対して走り続けて GitHub Actions の使用時間を浪費
- 開発者が「最新の commit の結果」を見たいのに古い結果に埋もれる
- `cancel-in-progress: true` により「常に最新コミットの結果だけが残る」運用になる

#### `jobs:` と `runs-on:`

```yaml
jobs:
  lint-and-format:
    runs-on: ubuntu-latest
```

| 値                | 用途                                          |
| ----------------- | --------------------------------------------- |
| `ubuntu-latest`   | 最も一般的、最速、最安(他 OS の約 1/10 のコスト) |
| `windows-latest`  | Windows 固有のテストが必要な時のみ            |
| `macos-latest`    | iOS / macOS ビルドが必要な時のみ              |
| `self-hosted`     | 自前ランナー                                  |

特別な理由がなければ **Ubuntu 一択**。

#### `steps:` の各種パターン

##### Action を使う(`uses:`)

```yaml
- uses: actions/checkout@v4
```

GitHub 公式 / 第三者の再利用可能なステップ。`@v4` でバージョンを固定。

##### コマンドを直接実行(`run:`)

```yaml
- run: pnpm lint
```

シェルコマンドを直接実行。

#### よく使う Action

| Action                       | 用途                                                                |
| ---------------------------- | ------------------------------------------------------------------- |
| `actions/checkout@v4`        | リポジトリチェックアウト(ほぼ全 CI で最初に必須)                |
| `actions/setup-node@v4`      | Node.js セットアップ + キャッシュ管理                              |
| `pnpm/action-setup@v4`       | pnpm セットアップ                                                  |
| `actions/cache@v4`           | 任意のディレクトリのキャッシュ管理                                 |
| `actions/upload-artifact@v4` | ビルド成果物を保存(後続ジョブで使う / UI からダウンロード可能) |
| `actions/download-artifact@v4` | upload した artifact を取得                                       |
| `softprops/action-gh-release@v2` | GitHub Release 自動作成                                          |

### 4.5 重要なテクニック

#### `--frozen-lockfile`(CI でのお作法)

```yaml
- run: pnpm install --frozen-lockfile
```

`pnpm-lock.yaml` を**変更しない**モード。lockfile と `package.json` に乖離があると CI が失敗します。

**なぜ必要か**:

- ローカルで `pnpm install` した時に lockfile を更新し忘れて push されると、CI 上で勝手に更新されて lockfile が変動する
- それを防ぐため CI では「lockfile を一切変更しない」と宣言
- 乖離があれば CI が失敗 → 開発者が気付いて lockfile を整合させて push し直す

ローカル開発では `pnpm install`(更新あり)、CI では `pnpm install --frozen-lockfile`(更新禁止)、という使い分けが定石。

npm の場合は `npm ci`、yarn の場合は `yarn install --frozen-lockfile` が同等の意味。

#### キャッシュの効果

`actions/setup-node@v4` の `cache: 'pnpm'` を指定すると、`pnpm-lock.yaml` をキーに `node_modules` の取得が高速化されます。

- 初回: 数十秒〜数分
- キャッシュヒット: 数秒で完了
- lockfile が変わったら自動で再生成(キャッシュ無効化)

これで月 2,000 分の無料枠を効率良く使えます。

#### Step の依存順序

```yaml
- uses: pnpm/action-setup@v4    # ← Node より先に pnpm
- uses: actions/setup-node@v4
  with:
    cache: 'pnpm'                # ← pnpm が先にないとここで失敗する
```

`setup-node` の `cache: 'pnpm'` は **pnpm が先にインストールされている前提**。順序を間違えると CI が失敗するので注意。

### 4.6 ジョブの並列化と依存

```yaml
jobs:
  lint:
    runs-on: ubuntu-latest
    steps: ...

  typecheck:
    runs-on: ubuntu-latest
    steps: ...

  test:
    runs-on: ubuntu-latest
    needs: [lint, typecheck]   # ← 前提ジョブ完了を待つ
    steps: ...

  deploy:
    runs-on: ubuntu-latest
    needs: [test]
    if: github.ref == 'refs/heads/master'   # ← master のみ実行
    steps: ...
```

| 機能       | 効果                                                |
| ---------- | --------------------------------------------------- |
| 複数 job   | 並列実行で全体時間を短縮                           |
| `needs:`   | 前提ジョブを指定(直列にしたい時)                |
| `if:`      | 条件付き実行(ブランチ・イベント・式で制御)      |

### 4.7 シークレット管理

API キーなどの機密情報は **GitHub Secrets** に登録して `${{ secrets.NAME }}` で参照します。

```yaml
- run: pnpm deploy
  env:
    VERCEL_TOKEN: ${{ secrets.VERCEL_TOKEN }}
    AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
```

設定場所: GitHub リポジトリ → Settings → Secrets and variables → Actions

| 種別                | 用途                                              |
| ------------------- | ------------------------------------------------- |
| Repository secret  | リポジトリ全体で利用                              |
| Environment secret | 環境別(production / staging 等)に分けて管理   |
| Organization secret | Org 全体で共有(複数リポジトリで使い回し)      |

**シークレットはログに出力されない**(GitHub が自動マスク)が、`echo` で意図的に出すこともできるので注意。

### 4.8 ブランチ保護ルール(CI を「強制」する設定)

CI を組んだだけでは「失敗してもマージできる」状態。**ブランチ保護ルール** で強制します。

設定場所: GitHub リポジトリ → Settings → Branches → Branch protection rules → 保護対象ブランチを指定

主要な設定:

- ✅ **Require status checks to pass before merging**(CI 成功必須)
- ✅ **Require branches to be up to date before merging**(merge 前に最新化)
- ✅ **Require pull request reviews before merging**(レビュー必須)
- ✅ **Include administrators**(管理者にも適用)

これで「未整形コードや lint エラーが master に入る」事故を構造的に防げます。

### 4.9 失敗の典型ケースと対処

| 失敗内容                                | 原因                                                                | 対処                                                                |
| --------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `pnpm install --frozen-lockfile` 失敗  | `package.json` 変更後に lockfile を更新せず push                   | ローカルで `pnpm install` → lockfile を含めて再 push              |
| `eslint .` 失敗                         | コードに lint エラーあり                                            | ローカルで `pnpm lint:fix`、それでも残るエラーは手動修正           |
| `prettier --check` 失敗                 | 整形漏れのコードを push                                            | ローカルで `pnpm format` → 差分を含めて再 push                     |
| Node バージョン不一致                   | `.nvmrc` と CI の Node バージョンがずれている                      | `.nvmrc` を修正                                                    |
| キャッシュが効かない / install が遅い | キャッシュキー(`pnpm-lock.yaml` のハッシュ)が変わった            | 仕様(lockfile が変わったらキャッシュ無効化されるのは正常)        |
| Action バージョンが取得できない         | `@v3` 等の古いバージョンが廃止された                              | 最新版にバージョンアップ                                            |

## 5. Vercel と自動デプロイ

### Vercel とは

**Next.js の開発元(Vercel Inc.)が運営する、フロントエンド特化のクラウドプラットフォーム**。「デプロイの簡単さ」と「Edge Network(CDN)の速さ」が最大の特徴。

主な機能:

- 静的サイト + サーバーレス関数のホスティング
- 世界 30 リージョン以上の Edge Network で配信
- GitHub / GitLab / Bitbucket と統合した自動デプロイ
- HTTPS 自動化、カスタムドメイン対応
- Image Optimization、Analytics、Speed Insights 内蔵

### 自動デプロイの基本フロー

```
[開発者] git push origin main
   ↓
[GitHub] Webhook 通知
   ↓
[Vercel] リポジトリを clone
   ↓
[Vercel] ビルド実行(Next.js なら zero-config)
   ↓
[Vercel] Edge Network に成果物をアップロード
   ↓
[本番 URL] 数秒〜数十秒で更新
```

### Preview デプロイ(Vercel の最大の強み)

PR ごとに **固有 URL を自動払い出す**:

| ブランチ                  | デプロイ先 | URL の形                                       |
| ------------------------- | ---------- | ---------------------------------------------- |
| `main`                    | 本番       | `https://example.app`                          |
| 他ブランチ(`feature/x`) | Preview    | `https://example-feature-x-{hash}.vercel.app`  |
| PR(`#42`)                | Preview    | `https://example-pr-42-{hash}.vercel.app`      |

メリット:

- レビュアーが **ブラウザで実機確認** できる
- PR コメントに自動で URL が貼られる(GitHub 統合)
- 複数 PR を並行で走らせても干渉しない
- 本番に影響しない

### Next.js との相性が完璧な理由

Next.js は Vercel 自身が作っているフレームワーク。以下が **設定なし(zero-config)** で動きます:

| 機能                  | 内容                                                  |
| --------------------- | ----------------------------------------------------- |
| Server Components     | サーバー側で React レンダリング、初期表示高速化      |
| ISR(再生成)         | 静的生成 + 一定時間で再生成、SEO とパフォーマンス両立 |
| Image Optimization    | 自動で WebP / AVIF 変換、サイズ最適化                |
| Edge Runtime          | サーバーレス関数を Edge で実行、レイテンシ < 50ms    |
| Streaming             | Server Components のストリーミング配信               |

他のホスティング(AWS Amplify / Netlify / Cloudflare Pages)では Next.js 機能の一部が制限されたり、手動セットアップが必要になります。

### 環境変数管理

| 環境タイプ      | 用途                                  |
| --------------- | ------------------------------------- |
| **Production**  | 本番デプロイ時に注入                  |
| **Preview**     | プレビュー(他ブランチ)で注入        |
| **Development** | `vercel dev` で注入(任意)           |

設定方法: Vercel ダッシュボード or CLI(`vercel env add`)。

#### `NEXT_PUBLIC_` プレフィックスの違い

- `NEXT_PUBLIC_API_URL`: ブラウザに公開される(クライアントサイドコードに埋め込まれる)
- `STRIPE_SECRET_KEY`: サーバーサイドのみ(SSR / API Routes / Server Components 内のみ参照可能)

**機密情報(API キー等)は絶対に `NEXT_PUBLIC_` を付けない**。

### ドメイン設定

| ドメイン種別          | 内容                                                |
| --------------------- | --------------------------------------------------- |
| Vercel 自動付与       | `<project>.vercel.app`(無料、即利用可)            |
| カスタムドメイン      | 独自ドメイン(無料設定可能、DNS レコード追加必要)  |
| HTTPS                 | Let's Encrypt 経由で自動発行・自動更新              |

### 料金プラン(2026 年時点)

| プラン         | 月額   | 用途                                              |
| -------------- | ------ | ------------------------------------------------- |
| **Hobby**      | $0     | 個人開発・学習。**商用利用不可**(規約上の制限)  |
| **Pro**        | $20/人 | 商用利用 OK、帯域 1TB、SSO、Audit Log なし        |
| **Enterprise** | カスタム | SSO、SLA、専任サポート、Audit Log                |

商用 SaaS をリリースするなら Pro 以上が必須(Hobby だと規約違反)。

### Monorepo(Turborepo)との連携

Vercel は Turborepo + pnpm Workspaces にネイティブ対応。

| 設定項目              | 値                                                     |
| --------------------- | ------------------------------------------------------ |
| **Root Directory**    | `apps/web`(Vercel が build を実行するディレクトリ)   |
| **Framework Preset**  | `Next.js`(自動検出される)                            |
| **Build Command**     | デフォルト or `cd ../.. && pnpm turbo build --filter web` |
| **Install Command**   | `pnpm install`                                         |
| **Output Directory**  | `.next`(Next.js デフォルト)                          |

Turborepo リモートキャッシュ統合により、CI ビルド時間を大幅短縮可能。

## 6. 関連用語の整理

| 用語                                       | 意味                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------- |
| **デプロイ**(Deploy)                     | コードを実行環境に配置する行為                                                              |
| **リリース**(Release)                    | デプロイされたコードを「ユーザーに提供する」状態にする(機能フラグで段階的に開放等)        |
| **ロールアウト**(Rollout)                | 段階的にユーザーへ展開していくプロセス(カナリアリリース等)                                |
| **ロールバック**(Rollback)               | 障害発生時に旧バージョンに戻すこと                                                          |
| **CI**(Continuous Integration)           | 自動テスト・lint 等の品質チェックを継続的に実施                                             |
| **CD**(Continuous Delivery / Deployment) | リリース可能な状態を保つ(Delivery)/ 自動で本番反映(Deployment)                          |
| **Blue-Green デプロイ**                   | 2 つの環境を用意し、切り替えで一気に新バージョンへ移行                                      |
| **カナリアデプロイ**                      | 一部のユーザーにだけ新バージョンを公開、問題なければ全展開                                  |
| **Edge Computing**                        | ユーザーに地理的に近い拠点(Edge)で処理を実行、レイテンシ削減                              |
| **CDN**(Content Delivery Network)        | 静的コンテンツを世界中の拠点にキャッシュして配信、高速化                                    |

## 7. モダン B2B SaaS の典型的なデプロイ構成

```
[フロント]
└── Next.js → Vercel(静的 + サーバーレス + Edge Network)
    └── git push → 自動デプロイ + Preview URL

[バック]
└── NestJS / Express → コンテナ PaaS(AWS ECS Fargate / Cloud Run)
    └── GitHub Actions でビルド → ECR(レジストリ)→ ECS 切り替え

[データベース]
└── マネージド DB(AWS RDS / Aurora / Cloud SQL / Supabase)
    └── マイグレーションツール(Prisma / Drizzle / Flyway)で管理

[キュー / キャッシュ]
└── マネージド Redis(AWS ElastiCache / Upstash)
```

このように、**1 つのアプリでもパーツごとに別のホスティングを使い、それぞれ異なるデプロイ方式**を取るのが現代のスタンダード。

## 8. ホスティング選定のチェックリスト

新規プロジェクトで選ぶ時の判断軸:

- [ ] フレームワークとの統合度(Next.js なら Vercel が最強)
- [ ] 商用利用可否(Vercel Hobby は不可、Cloudflare Pages は OK 等)
- [ ] スケール時のコスト(従量課金 / 固定 / ハイブリッド)
- [ ] グローバル配信(Edge Network の有無)
- [ ] 環境変数 / シークレット管理
- [ ] カスタムドメイン対応
- [ ] Preview デプロイの有無(レビュー時の負担を大きく削減)
- [ ] チーム機能(SSO、Audit Log)
- [ ] サポート体制(SLA、専任サポートの有無)
- [ ] ベンダーロックの程度(他に移しやすいか)
